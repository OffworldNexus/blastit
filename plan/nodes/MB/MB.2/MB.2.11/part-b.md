# PgBouncer (part B): pooling semantics, prepared statements, auth, healthcheck, image

- Node: MB.2.11 · Author: researcher · Date: 2026-11-13
- All PgBouncer-hosted pages fetched and quoted 2026-11-13; probes run in `/tmp/opencode` against `edoburu/pgbouncer:v1.26.1-p0` + `postgres:18` (Docker), commands reproducible from the bullets below.

## B1. `pool_mode=transaction` and exactly what breaks
- Definition: `session` = "Server is released back to pool after client disconnects. Default."; `transaction` = "Server is released back to pool after transaction finishes."; `statement` = "… after query finishes" (<https://www.pgbouncer.org/config.html#pool_mode>).
- Features page wording: "A server connection is assigned to a client only during a transaction. When PgBouncer notices that the transaction is over, the server will be put back into the pool." … "This mode breaks a few session-based features of PostgreSQL. You can use it only when the application cooperates by not using features that break." (<https://www.pgbouncer.org/features.html>).
- Per-feature table, transaction column (<https://www.pgbouncer.org/features.html>): `SET`/`RESET` **Never**; `LISTEN` **Never**; `NOTIFY` **Yes**; `WITHOUT HOLD` cursor Yes; `WITH HOLD` cursor **Never**; protocol-level prepared plans **Yes** (needs `max_prepared_statements` ≠ 0); SQL `PREPARE`/`DEALLOCATE` **Never**; `ON COMMIT DROP` temp tables Yes; `PRESERVE`/`DELETE ROWS` temp tables **Never**; cached plan reset Yes; `LOAD` **Never**; session-level advisory locks **Never**.
- "Never" means *silently wrong*, not rejected: the statement runs on whichever server connection is attached. Probe (`pool_mode=transaction`): `BEGIN; SET timezone='UTC'; COMMIT;` then `SHOW timezone` returned `UTC`; `LISTEN chan1` returned `LISTEN`; `pg_try_advisory_lock(42)` returned `t` and the lock was visible from the next transaction of the same client — all because a pool of one re-linked the same server connection. With >1 server connections the same sequence is a coin flip; the docs are the authority, not the single-connection probe.
- `server_reset_query` (`DEFAULT DISCARD ALL`) "is not used" in transaction pooling, "because in that mode, clients must not use any session-based features, since each transaction ends up in a different connection and thus gets a different session state" (<https://www.pgbouncer.org/config.html#server_reset_query>). `server_reset_query_always=1` is the documented "working around broken setups … changes non-deterministic breakage to deterministic breakage" knob.
- `SET` nuance: parameters PgBouncer *tracks* (`TimeZone`, `application_name`, `DateStyle`, `IntervalStyle`, `client_encoding`, `standard_conforming_strings`, `search_path` PG18+, `default_transaction_read_only` PG14+, `scram_iterations` PG16+, `session_authorization`) are cached per client connection and "restored in the server whenever the client becomes active" — that is why the probe above saw `UTC`. Untracked parameters changed with `SET` "leak to other clients sharing the server connection, unless `server_reset_query_always` is used" (<https://www.pgbouncer.org/config.html#track_extra_parameters>).
- Prepared statements in transaction mode are the documented exception: since 1.21 they work, but only through the `max_prepared_statements` mechanism (B2), not through SQL `PREPARE`.

## B2. `max_prepared_statements`
- Introduced in **1.21.0** (2023-10-16, "The one with prepared statements"): "Add support for protocol-level named prepared statements! … you need to change the new `max_prepared_statements` setting to a non-zero value" (<https://www.pgbouncer.org/changelog.html>). FAQ: "Since version 1.21.0 PgBouncer can track prepared statements in transaction pooling mode … `max_prepared_statements` needs to be set to a non-zero value" (<https://www.pgbouncer.org/faq.html>).
- **DEFAULT is 200**, not 0: "Default: 200" (<https://www.pgbouncer.org/config.html#max_prepared_statements>); raised from 0 in 1.24.0 ("Enable prepared statement support by default, `max_prepared_statements` is now set to 200 by default", <https://www.pgbouncer.org/changelog.html>). Probe: `SHOW CONFIG` on the image returns `max_prepared_statements|200|200|yes`.
- What it does: "tracks protocol-level named prepared statements related commands sent by the client in transaction and statement pooling mode"; each unique query string gets an internal name `PGBOUNCER_{unique_id}`, the client-side name is rewritten, and the statement is transparently prepared on whichever server connection the client gets; "The actual value … controls the number of prepared statements kept active in an LRU cache on a single server connection" (<https://www.pgbouncer.org/config.html#max_prepared_statements>).
- Only transaction/statement pooling: the config text says "in transaction and statement pooling mode", and the macro is `connection_pool_mode(x) != POOL_SESSION && cf_max_prepared_statements != 0` (<https://github.com/pgbouncer/pgbouncer/blob/master/include/prepare.h>). Session pooling instead needs `server_reset_query = DISCARD ALL` or `DEALLOCATE ALL` (<https://www.pgbouncer.org/faq.html>).
- Protocol-level = extended query protocol `Parse`/`Bind`/`Describe`/`Close`. SQL-level statements are **not** tracked: "`PREPARE`, `EXECUTE` and `DEALLOCATE` are forwarded straight to Postgres. The exception … `DEALLOCATE ALL` and `DISCARD ALL`" (<https://www.pgbouncer.org/config.html#max_prepared_statements>).
- Error text when it is **0**: config.html documents no error string; PgBouncer simply forwards `Parse`/`Bind` unchanged, so the failure is PostgreSQL's own. PostgreSQL source strings: `prepared statement "%s" already exists` (`ERRCODE_DUPLICATE_PSTATEMENT`) and `prepared statement "%s" does not exist` (`ERRCODE_UNDEFINED_PSTATEMENT`) (<https://github.com/postgres/postgres/blob/master/src/backend/commands/prepare.c>). Probe, `MAX_PREPARED_STATEMENTS=0`, `DEFAULT_POOL_SIZE=1`, two sequential psycopg 3 clients with `prepare_threshold=0`: `psycopg.errors.DuplicatePreparedStatement: prepared statement "_pg3_0" already exists`; the identical run against `max_prepared_statements=200` succeeded.
- Other documented operational cost: reusing one prepared plan across clients can raise `ERROR: cached plan must not change result type`; fix is `RECONNECT` after DDL migrations (<https://www.pgbouncer.org/config.html#max_prepared_statements>) — this is why the migration URL must bypass the pooler.

## B3. Pool sizing defaults (<https://www.pgbouncer.org/config.html>)
| Setting | Semantics | Default |
|---|---|---|
| `default_pool_size` | max server connections per user/database pair; overridable per db/user | **20** (0 = unlimited since 1.24.0, changelog) |
| `max_client_conn` | max client connections; fd budget is `max_client_conn + (max pool_size * total databases * total users)` | **100** |
| `reserve_pool_size` | extra connections allowed on top of the pool; 0 disables | **0** |
| `reserve_pool_timeout` | seconds a client may wait before reserve connections are used; 0 disables | **5.0** |
| `min_pool_size` | pre-open server connections; "effectively capped at the pool size"; only for forced-user pools or pools with ≥1 client | **0** (disabled) |
| `max_db_connections` | hard cap per PgBouncer database, regardless of user | **0** (unlimited) |
- Adjacent timeouts worth documenting: `query_wait_timeout` 120.0 (client disconnected if no server for that long), `server_idle_timeout` 600.0, `server_lifetime` 3600.0, `server_check_delay` 30.0, `client_login_timeout` 60.0 (<https://www.pgbouncer.org/config.html>).

## B4. Authentication (<https://www.pgbouncer.org/config.html#authentication-settings>)
- `auth_type` values: `cert` (TLS client cert, user from CN), `md5` (**default**; auth_file may hold MD5 or plaintext; "If `md5` is configured and a user has a SCRAM secret, then SCRAM authentication is used automatically instead"), `scram-sha-256` ("auth_file has to contain SCRAM secrets or plain-text passwords"), `plain` (deprecated), `trust` (no auth, "user name must still exist in auth_file"), `any` (like trust but user name ignored; requires forced users in all databases; console allows any user as admin), `hba` (rules from `auth_hba_file`), `ldap`, `pam` ("auth_file is ignored", incompatible with `auth_user`).
- Which types need a user source: "Most authentication types … require that either `auth_file` or `auth_user` be set; otherwise there would be no users defined" (<https://www.pgbouncer.org/config.html#auth_file>). `cert`/`hba`+`peer` can avoid a password; `pam` and `any` do not use `auth_file`.
- `userlist.txt` (`auth_file`) format: `"username" "password"` or `"username" "md5<md5(password+username)>"` or `"username" "SCRAM-SHA-256$<iterations>:<salt>$<storedkey>:<serverkey>"`; "at least 2 fields, surrounded by double quotes … PgBouncer ignores the rest of the line" (<https://www.pgbouncer.org/config.html#authentication-file-format>).
- Limitation that decides the design: a SCRAM secret "can only be used for logging into a server if the client authentication also uses SCRAM, the PgBouncer database definition does not specify a user name, and the SCRAM secrets are identical in PgBouncer and the PostgreSQL server (same salt and iterations)" (<https://www.pgbouncer.org/config.html#authentication-file-format>). A forced `user=` in `[databases]` therefore forces plaintext for SCRAM backends.
- `auth_query` + `auth_user`: any user not in `auth_file` is looked up in `pg_authid` via `auth_query` using `auth_user`, whose password comes from `auth_file`; "Direct access to `pg_authid` requires admin rights. It's preferable to use a non-superuser that calls a SECURITY DEFINER function instead"; the query runs inside the target database, returns (user, password) and "must return two columns"; default is `SELECT rolname, CASE WHEN rolvaliduntil < now() THEN NULL ELSE rolpassword END FROM pg_authid WHERE rolname=$1 AND rolcanlogin` (<https://www.pgbouncer.org/config.html#auth_query>). Per-database `auth_user`/`auth_query`/`auth_dbname`/`password` overrides exist, but "Dynamic forms of password discovery such as `auth_query` are not currently supported" for a `password=` in a database connection string (<https://www.pgbouncer.org/config.html#section-databases>).
- `mkauth.py` exists to generate `userlist.txt` from `pg_authid` (<https://www.pgbouncer.org/config.html#authentication-file-format>).
- Best practice for Blastit: terminate app auth in Blastit's dbproxy, and let dbproxy authenticate to PgBouncer with SCRAM (`auth_type = scram-sha-256`, one dedicated pooler role via `auth_user` + SECURITY DEFINER `auth_query`, or a SCRAM secret in `userlist.txt`). Avoid `trust`/`any`/`plain`; never keep a plaintext `userlist.txt`.

## B5. Healthcheck
- The image ships **no** Docker healthcheck: the `Dockerfile` ends at `ENTRYPOINT`/`CMD` with no `HEALTHCHECK`, `EXPOSE 5432`, `USER postgres` (<https://github.com/edoburu/docker-pgbouncer/blob/master/Dockerfile>); `docker inspect` confirms `Healthcheck=<nil> Exposed=5432/tcp User=postgres`. It bundles `postgresql-client`, i.e. `pg_isready`, and "Uses standard Postgres port 5432" (<https://github.com/edoburu/docker-pgbouncer>), so the probe is `pg_isready -h 127.0.0.1 -p 5432 -U <user>` — **not** 6432 (6432 is only the PgBouncer compile-time default, <https://www.pgbouncer.org/config.html#listen_port>).
- `pg_isready` is safe with `pool_mode=transaction`: it only reads the first server response and needs no valid credentials — "It is not necessary to supply correct user name, password, or database name values to obtain the server status" (<https://www.postgresql.org/docs/current/app-pg-isready.html>). Probe: with `auth_type=scram-sha-256`, transaction mode, `pg_isready -U ghost -d ghostdb` printed `accepting connections`, `exit=0`; PgBouncer answers the startup packet with an auth request before resolving user/database (missing users are reported after authentication, <https://www.pgbouncer.org/changelog.html>), so pool mode and auth are irrelevant.
- `psql -c 'SHOW POOLS'` is a *backend-aware* probe but is not portable as a container healthcheck: the console lives in the virtual database `pgbouncer`, only `admin_users`/`stats_users` may log in, and "The admin console currently only supports the simple query protocol. Some drivers use the extended query protocol for all commands; these drivers will not work for this" (<https://www.pgbouncer.org/usage.html>). Probe: `psql … dbname=pgbouncer -c "SHOW POOLS"` works; psycopg 3 against the same console fails with `ProtocolViolation invalid command 'BEGIN', use SHOW HELP;`. `SHOW POOLS` rows are per `(database, user)` pair with `cl_active`, `cl_waiting`, `sv_active`, `sv_idle`, `sv_used`, `maxwait` — the right signal that the *backend* pool is starved (<https://www.pgbouncer.org/usage.html>).

## B7. `ignore_startup_parameters` / `track_extra_parameters`
- Documented default of `ignore_startup_parameters` is **empty**, and "By default, PgBouncer allows only parameters it can keep track of in startup packets … All other parameters will raise an error" (<https://www.pgbouncer.org/config.html#ignore_startup_parameters>). The edoburu entrypoint overrides it to `extra_float_digits`.
- Unknown top-level startup parameter → connection rejected; probe with a hand-built startup packet: `unsupported startup parameter: foo` (SQLSTATE `08P01`). Unknown parameter *inside* `options` → `unsupported startup parameter in options: statement_timeout` (probe: `options='-c statement_timeout=5000'`).
- `options=-c timezone=UTC` **is accepted by default** and does reach the server in transaction mode: `TimeZone` is in the default tracked set, and "Parameters specified using both of these methods are supported by `track_extra_parameters` … However, it's not possible to include `options` itself in `track_extra_parameters`, only the parameters contained in `options`" (<https://www.pgbouncer.org/config.html#track_extra_parameters>). Probe through the pooler: `psql "… options='-c timezone=UTC'" -Atc "show timezone"` → `UTC`, versus `Etc/UTC` without it. `options` support itself landed in 1.20.0 (<https://www.pgbouncer.org/changelog.html>).
- Non-tracked parameters in `options` need `track_extra_parameters=<name>` (mounted ini) — putting `options` in `ignore_startup_parameters` only makes PgBouncer *ignore* them, i.e. they never reach PostgreSQL.

## Developer Experience Implications
- Out of the box (compose) the minimum honest config is 4 env lines: `DATABASE_URL`, `POOL_MODE=transaction`, `AUTH_TYPE=scram-sha-256`, `MAX_PREPARED_STATEMENTS=200` (explicit even though 200 is the default, so the preset documents intent and survives an image downgrade to 1.21–1.23 where the default is 0).
- `options=-c timezone=UTC` in the app's `DATABASE_URL` needs **no** pooler setting and no `track_extra_parameters`, which is exactly the zero-config replacement for Django's connect-time `SET TIME ZONE` that MB.2.11 wants: one query parameter, no mounted ini, no extra grant.
- The two-URL rule is forced by the docs, not by taste: migrations must bypass the pooler because `PREPARE`/`DEALLOCATE` and DDL-cached plans break under transaction pooling, and `RECONNECT` is the documented recovery (<https://www.pgbouncer.org/config.html#max_prepared_statements>).
- Healthcheck is one line the user must add themselves (`pg_isready -h 127.0.0.1 -p 5432 -U $DB_USER`), since the image ships none; keep it on 5432 and never use `SHOW POOLS` in a healthcheck.
- Pin `v1.26.1-p0`, not `latest`, and set `AUTH_TYPE=scram-sha-256`: the md5 default silently fails against a modern PostgreSQL, which is the single most likely first-run failure of this preset.
- Caution for the preset text: `auth_type=md5` + `userlist.txt` plaintext means the pooler itself becomes a credential store. If Blastit's dbproxy already authenticates the app, the pooler should hold exactly one SCRAM role and nothing else.
