# psycopg 3 + Django behind a transaction-mode pooler (PgBouncer / DO managed pooler)
- Node: MB.2.11 (part C) · Author: researcher · Date: 2026-11-13

## TL;DR
- psycopg 3 prepares a query after it has been executed **more than 5** times *on the same connection*: `prepare_threshold=5` default, `prepared_max=100` ([docs](https://www.psycopg.org/psycopg3/docs/api/connections.html#psycopg.Connection.prepare_threshold)).
- Disable with `prepare_threshold=None` (connect kwarg or attribute); Django 4.2+ **already does this** for psycopg 3 (`conn_params["prepare_threshold"] = conn_params.pop("prepare_threshold", None)`), so Django apps do not break on poolers by default ([source](https://github.com/django/django/blob/stable/5.2.x/django/db/backends/postgresql/base.py#L297-L300)).
- Django's default psycopg 3 cursor is `ClientCursor`, whose `_get_prepared()` returns `Prepare.NO` — Django never prepares any statement unless `OPTIONS={"server_side_binding": True}` ([source](https://github.com/psycopg/psycopg/blob/master/psycopg/psycopg/client_cursor.py#L80-L83)).
- Without pooler-side tracking the server errors are exactly `prepared statement "_pg3_0" already exists` (SQLSTATE 42P05) / `prepared statement "_pg3_0" does not exist` (26000) ([prepare.c#L411](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/commands/prepare.c#L411), [#L450](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/commands/prepare.c#L450)).
- `options=-c timezone=UTC` is a **libpq startup parameter**; the server applies it as a session default and reports `UTC` in `ParameterStatus`, so psycopg's `conn.info.parameter_status("TimeZone")` returns `"UTC"` (probed below).
- Consequence: Django's `_configure_timezone` sees a match and **skips** `SELECT set_config('TimeZone', %s, false)` when it wants UTC. It fires once per connection only when the DB-level timezone differs.

## Developer Experience Implications
- Zero-config path: `DATABASE_URL=postgresql://…?options=-c%20timezone%3DUTC&sslmode=require` (or Django `OPTIONS={"options": "-c timezone=UTC"}`) is enough; no pooler tuning, no `prepare_threshold` knob, no per-request `SET TIME ZONE`. Django 4.2+/psycopg 3 defaults are already pooler-safe.
- Do **not** inject `channel_binding=require` into a pooler DSN: PgBouncer refuses it (`could not connect to server: channel binding is required, but server did not offer an authentication method that supports channel binding`) — use `prefer` (libpq default) and get pooler identity from `sslmode=verify-full` against the pooler cert ([issue #522](https://github.com/pgbouncer/pgbouncer/issues/522)).
- `sslmode` verifies the **pooler's** certificate, not the origin server's; origin TLS must be configured on the pooler (`server_tls_sslmode`) — Blastit docs should say "TLS ends at the pooler" rather than imply end-to-end pinning.
- Only GUCs the pooler can track belong in `options`: PgBouncer checks parameters inside `options` and rejects unknown ones unless listed in `ignore_startup_parameters` (e.g. `options,extra_float_digits`) ([config](https://www.pgbouncer.org/config.html#ignore_startup_parameters)).

## Technical Findings
### C1 — when psycopg 3 prepares
- "A query is prepared automatically after it is executed more than `prepare_threshold` times on a connection"; `prepare_threshold=5`, `prepared_max=100`; `prepared_max=None` disables deallocation ([prepare.html](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html), [connections.html](https://www.psycopg.org/psycopg3/docs/api/connections.html#psycopg.Connection.prepare_threshold)).
- Probe (below): 5 executions → 0 server prepared statements; 6th execution → `_pg3_0`. Statement names are `_pg3_N`, which is why the errors above quote `"_pg3_0"`.
- Disable: `psycopg.connect(..., prepare_threshold=None)` (kwarg since 3.1) or `conn.prepare_threshold = None` ([prepare.html](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html)).
- psycopg's own warning: "Unless a connection pooling middleware explicitly declares otherwise, they are not compatible with prepared statements, because the same client connection may change the server session it refers to." ([prepare.html](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html)).
- Exact wording is server-side, not psycopg: `prepared statement "%s" already exists` / `prepared statement "%s" does not exist` ([prepare.c](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/commands/prepare.c#L411)), codes 42P05 / 26000 ([errcodes](https://www.postgresql.org/docs/current/errcodes-appendix.html)).

### C2 — libpq `options`
- "Specifies command-line options to send to the server at connection start. For example, setting this to `-c geqo=off` … sets the session's value of the `geqo` parameter to off." Spaces separate arguments unless backslash-escaped ([libpq-connect](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-PARAMKEYWORDS)).
- psycopg 3 passes any libpq keyword as `connect(**kwargs)` "Further parameters specifying the connection string. They override the ones specified in conninfo", and points at the libpq keyword list as the accepted set — so `options=` / `options=` in the URL both work ([connections.html](https://www.psycopg.org/psycopg3/docs/api/connections.html#psycopg.Connection.connect)).

### C3 — Django `_configure_timezone` and OPTIONS passthrough
- Code ([base.py#L351-L358](https://github.com/django/django/blob/stable/5.2.x/django/db/backends/postgresql/base.py#L351-L358)):
  `conn_timezone_name = connection.info.parameter_status("TimeZone")`; `timezone_name = self.timezone_name`; `if timezone_name and conn_timezone_name != timezone_name:` → `cursor.execute(self.ops.set_time_zone_sql(), [timezone_name])`.
- `set_time_zone_sql()` is exactly `"SELECT set_config('TimeZone', %s, false)"` ([operations.py#L204-L205](https://github.com/django/django/blob/stable/5.2.x/django/db/backends/postgresql/operations.py#L204-L205)); `is_local=false` makes it session-wide, not transaction-local ([functions-admin](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADMIN-SET)).
- Compared value is **not** `settings.TIME_ZONE` directly: `timezone_name` = `settings.TIME_ZONE` if `not USE_TZ`, else `DATABASES[...]["TIME_ZONE"]` or `"UTC"` ([base.py#L158-L167](https://github.com/django/django/blob/stable/5.2.x/django/db/backends/base/base.py#L158-L167)); docs confirm "if not None, or to UTC otherwise" ([settings](https://docs.djangoproject.com/en/5.2/ref/settings/#time-zone)).
- It runs at connect: `_configure_connection` calls it, then `init_connection_state` commits if it returned True and the connection is not autocommit ([base.py#L349-L405](https://github.com/django/django/blob/stable/5.2.x/django/db/backends/postgresql/base.py#L349-L405)).
- `OPTIONS` passthrough is dict unpacking into the connect kwargs: `conn_params = {"dbname": …, **settings_dict["OPTIONS"]}` then `self.Database.connect(**conn_params)` ([#L257-L259](https://github.com/django/django/blob/stable/5.2.x/django/db/backends/postgresql/base.py#L257-L259), [#L332](https://github.com/django/django/blob/stable/5.2.x/django/db/backends/postgresql/base.py#L332)) — so `OPTIONS: {"options": "-c timezone=UTC"}` reaches libpq verbatim. (5.2 uses unpacking, not `conn_params.update(...)`.)
- Django docs: connection parameters are set up on connect and are not repeated with persistent connections; time zone is named as such a parameter ([databases](https://docs.djangoproject.com/en/5.2/ref/databases/#persistent-connections)).

### C4 — does the `set_config` query get prepared?
- No, twice over: (1) Django sets `prepare_threshold=None` by default for psycopg 3 (4.2 through 5.2.x), opted in only via `OPTIONS={"prepare_threshold": 5}` ([base.py#L297-L300](https://github.com/django/django/blob/stable/5.2.x/django/db/backends/postgresql/base.py#L297-L300)); (2) `_configure_timezone` executes on Django's `Cursor`, which subclasses psycopg's `ClientCursor` ([base.py#L576](https://github.com/django/django/blob/stable/5.2.x/django/db/backends/postgresql/base.py#L576)), and `ClientCursorMixin._get_prepared()` unconditionally returns `(Prepare.NO, b"")` ([client_cursor.py#L80-L83](https://github.com/psycopg/psycopg/blob/master/psycopg/psycopg/client_cursor.py#L80-L83)).
- Even with a server-binding cursor the threshold counts executions *on that connection* ([prepare.html](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html)), and this query runs once per connection ⇒ 1 < 5, never prepared.
- Transaction/autocommit: `set_config(..., false)` is session-scoped, so the commit Django issues right after (`init_connection_state`) does not revert it; psycopg connection defaults to `autocommit=False`, so the statement runs in an implicit transaction that Django commits ([functions-admin](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADMIN-SET), [base.py#L400-L405](https://github.com/django/django/blob/stable/5.2.x/django/db/backends/postgresql/base.py#L400-L405)).

### C5 — `sslmode` / `channel_binding` through a pooler
- PgBouncer is the TLS endpoint: `client_tls_sslmode` ("TLS mode to use for connections from clients", default `disable`) with `client_tls_key_file`/`client_tls_cert_file`; upstream TLS is separate (`server_tls_sslmode`, default `prefer`) ([config](https://www.pgbouncer.org/config.html#client_tls_sslmode)). So `sslmode=verify-full` validates **PgBouncer's** cert/hostname; origin verification is `server_tls_sslmode=verify-full` + `server_tls_ca_file` (INFERRED from the two independent settings, both documented).
- `channel_binding`: libpq `require` demands SCRAM channel binding "only supported over SSL connections with PostgreSQL 11 or later servers using the SCRAM authentication method" ([libpq](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-CHANNEL-BINDING)).
- PgBouncer does **not** implement it: changelog 1.12.0 "PgBouncer does not support channel binding. This change just fixes support for clients that offer it" ([changelog](https://www.pgbouncer.org/changelog.html)); current source logs "client requires SCRAM channel binding, but it is not supported" ([scram.c](https://raw.githubusercontent.com/pgbouncer/pgbouncer/master/src/scram.c)). VERIFIED: `channel_binding=require` fails through PgBouncer; clients must use `prefer`/`disable`.

### C6 — PgBouncer `max_prepared_statements >= 1` (1.21+)
- 1.21.0 added protocol-level prepared-statement tracking in transaction/statement pooling ([changelog](https://www.pgbouncer.org/changelog.html), [config](https://www.pgbouncer.org/config.html#max_prepared_statements)).
- **But psycopg's default does not just work on 1.21**: psycopg ≥3.2 requires PgBouncer **≥1.22**, `max_prepared_statements > 0`, and client libpq **≥17** (for `Close` of prepared statements); otherwise set `prepared_max=None` (no deallocation) or `prepare_threshold=None` ([prepare.html](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html)). 1.22.0 added `DEALLOCATE ALL`/`DISCARD ALL` support ([changelog](https://www.pgbouncer.org/changelog.html)).
- Default `max_prepared_statements` is **200** since 1.24.0 ("Enable prepared statement support by default") ([changelog](https://www.pgbouncer.org/changelog.html), [config](https://www.pgbouncer.org/config.html#max_prepared_statements)).
- For Django this is moot out of the box (C4: `prepare_threshold=None` + `ClientCursor`). Opting in requires `OPTIONS={"prepare_threshold": 5, "server_side_binding": True}` **and** the 1.22/libpq-17 matrix, plus `RECONNECT` after DDL to avoid "cached plan must not change result type" ([config](https://www.pgbouncer.org/config.html#max_prepared_statements)).

## (a)(b)(c) — if the app passes `options=-c timezone=UTC`, does Django still run `set_config`?
- (a) **VERIFIED (probe + docs):** the server applies startup parameters as session defaults and reports them in `ParameterStatus`; `TimeZone` is in the ParameterStatus set, and psycopg's `parameter_status()` tracks updates ([protocol-flow](https://www.postgresql.org/docs/current/protocol-flow.html#PROTOCOL-ASYNC), probe below: `parameter_status("TimeZone") == "UTC"`, `SHOW TimeZone == UTC`).
- (b) Django compares that value to `self.timezone_name`. `TIME_ZONE="UTC"` (DB-level option, or global with `USE_TZ=False`) → equal → **no `set_config`**. `TIME_ZONE="America/New_York"` → mismatch → **one** `SELECT set_config('TimeZone', 'America/New_York', false)` per connection ([base.py#L351-L358](https://github.com/django/django/blob/stable/5.2.x/django/db/backends/postgresql/base.py#L351-L358)). Subtlety: with `USE_TZ=True` the global `settings.TIME_ZONE` does **not** drive the DB session — Django wants UTC unless `DATABASES["default"]["TIME_ZONE"]` is set ([base.py#L158-L167](https://github.com/django/django/blob/stable/5.2.x/django/db/backends/base/base.py#L158-L167), [settings docs](https://docs.djangoproject.com/en/5.2/ref/settings/#time-zone)).
- (c) **Yes, unnecessary when it matches** — the branch is a pure equality check on the reported session value, so `options=-c timezone=UTC` makes the `set_config` round trip disappear. It is also the *safer* of the two behind a transaction pooler: PgBouncer tracks `TimeZone` by default and replays a client-known value on new server connections, while an `options`-only GUC is applied at server-connection startup ([track_extra_parameters](https://www.pgbouncer.org/config.html#track_extra_parameters)) — mark the replay behaviour INFERRED; it was not exercised against a live pooler.

## Empirical probes (`/tmp/opencode/mb211`, PostgreSQL 18.7, psycopg 3.3.9)
- `psycopg.connect(DSN, options="-c timezone=UTC")` → `parameter_status(TimeZone) = UTC`, `show TimeZone = UTC`.
- default connection, `SELECT 42` repeated: executions 1–5 → 0 rows in `pg_prepared_statements`; execution 6 → 2 rows (`_pg3_0`, `_pg3_1`, the counter query itself); `prepare_threshold=None` → 0 after 7 executions; `prepare_threshold=5`, `prepared_max=100`.
- `PREPARE _pg3_0 …` twice → `ERROR: prepared statement "_pg3_0" already exists`; after `DEALLOCATE`, `EXECUTE _pg3_0` → `ERROR: prepared statement "_pg3_0" does not exist`.
- `SELECT set_config('TimeZone','America/New_York',false)` → `parameter_status` flips to `America/New_York` (psycopg caches ParameterStatus on change).
