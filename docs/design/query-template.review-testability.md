## Arithmetic re-check (asked for explicitly)

Origin rule (§13.4.5): 1-based line, 1-based **char** column, origin = the first character
*inside* the opening quote. With the reference's 8-space indent the opening quote is column 15
and the origin column 16.

| Site | Decoded prefix | Recomputed | Verdict |
|---|---|---|---|
| `query ''` (`9:16`) | empty; site = closing quote | 8 spaces + `query ` + two quotes → closing quote at col 16 | **correct** |
| `query 'SELECT 1; SELECT 2'` (`11:26`) | `SELECT 1; ` = 10 chars | 16 + 10 = 26 | **correct** |
| `query 'SELECT id FROM ...'` (`13:31`) | `SELECT id FROM ` = 15 chars | 16 + 15 = 31 | **correct** |

The three reference-page sites are arithmetically right. The **LSP P7 worked example is
wrong** (finding T5): for `"view v \"/😀é\" { body = }"` the `=` is at char index **20**,
UTF-16 index **21**, byte **24**, with **18** ASCII bytes before it — the document says
19 / 20 / 23 / 17, i.e. P2's char and UTF-16 numbers with only the byte count bumped for `é`.

## What holds

- The three reference sites (9:16 / 11:26 / 13:31) are arithmetically correct under the stated
  origin rule, and P1, P2, P3, P5, H1–H6, C1, C4–C8 each name a concrete fixture, an exact
  value and a defect that reddens them.
- `TooLong`, `TooManyParameters`, `Empty`, `MultipleStatements`, `StrayEllipsis` and `Syntax`
  are all reachable from an unprivileged unit test, and the expansion table's rows 1–5 have a
  named case each in `MB.34.3`'s acceptance list.
- A new `crates/blastit-sqlpolicy/tests/critical_query_template.rs` is picked up by
  `make check` automatically (`rs-test-critical` walks `crates/*/tests/critical_*.rs`), and
  additions to the critical tier are always allowed by `critical_guard.py`.
- The `"…"`/`'…'` fixture contradiction in C3 was fixed in the version judged (it now uses the
  `"…"` spelling and adds a `'…'` `$1` twin), and §2.3's capability document already carries
  `codeActionProvider: true`.
