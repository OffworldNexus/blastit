# Security review — `MB.3.9.2` amendment (derived pool socket, optional `workers`)

**Status:** **FAIL — 0 BLOCKER, 3 MAJOR, 8 MINOR.**
**Lens:** `security` only (zero-trust, CVE resistance, fail-closed). DX/AI/testability not graded here.
**Scope:** only the 2026-11-14 amendment labelled `MB.3.9.2` — `docs/design/php-fastcgi.md` §1.2–§1.4, §3 `R3`/`R4`/`R20`, §4.1 (`SocketProbe`/`SocketProbeError`/`DevProbe`), §4.5.2 (Connection + Socket identity), §4.8.1 (derivation, `workers`, handoff, negative rule, `PinnedSocket` dev paragraph), §4.8.2 (Command, Pool file, workers rows), §4.8.3 (`B1`, `B2`, `S0`–`S7`, `U1`, `C1`, "Why creation is `0700`…", "What this amendment moved…"), §5.1 — plus `docs/decisions/ADR-0008-fastcgi-backend-and-param-lockdown.md` `**Amends.**` (271-335).
**Method:** attacked as an attacker holding only the manifest and the app: route names, `entry`, `static.root`, `workers`, `prefork`, `spa`, symlinks planted anywhere in the derived chain, a surviving `setsid()` escapee during the bind window, a rewritten pool file, and a hostile leftover across an init restart. Verified the cited code facts (`crates/blastit/src/config.rs:1301-1321,1407-1411`, `:674,677,841-842`; `crates/blastit/src/zygote.rs:52,115-121`) rather than trusting the doc.

## 2. The six attacker questions, answered

**(1) Can any manifest value reach the socket's path, leaf, parent, owner, mode, or pool?**
No for path/leaf/parent/owner/mode. `listen` is refused by the strict parser as `UnknownKey` (`:359`), `R3` derives from `<run>/fastcgi/<RouteInfo index>/fpm.sock` with no name interpolation (`:210-219`), `B1` requires `<runtime>` to be `init_uid 0700` with a non-route-writable path from `/`, and `B2` creates and pins the per-route parent itself, so the pre-amendment classes (two routes → one pool, `listen.mode`, a route-writable parent, a route-owned `manifest_dir` renamed under the pool) are gone, not policed. A symlink planted at `fastcgi` or `<i>` is refused before any route process exists (`ForeignOwner`/`Symlink`/`NotDirectory`), and after `B3` the parent is unsymlinked by mode. A rename of `.../<i>` is impossible at every phase: `fastcgi` is `init 0700` and is never chowned, so `route_uid` never has write on the directory's *parent*, only on the directory's entries. Manifest influence is limited to (a) the route *ordinal*, which also selects the uid, so the pair stays consistent (see S-8 for the one numbering ambiguity), (b) `workers` (size, S-1), and (c) `entry`/`manifest_dir`, which reach the pool *file* (`open_basedir`, `chdir`), not `listen=` (S-4/S-5).

**(2) Does the create→pin→bind→freeze→`S4`/`S6` sequence leave a rebind/plant/rename window?**
Per step, no: `S1` reaches `ECHILD` before `S2` opens write; `S4` requires `S_ISSOCK`+`nlink==1`+inode in a new-pgid task; `S5`'s `AT_SYMLINK_NOFOLLOW` plus the `O_PATH` fallback cannot chown a symlink target; `S6` re-verifies `(dev,ino)`, owner, mode and re-runs the pgid check after the freeze, so an `S4→S5` or `S5→S6` swap is caught. `U1` freezes before unlinking, so no `0755` tail. What the sequence does **not** survive is *iteration*: a second boot (S-2) and a hostile leftover at the leaf (S-3). The steady `0555` enables only `readdir` (S-6); `connect` needs write on the `0600 scheduler_uid` inode, and `SeccompRole::Scheduler` forbids `AF_INET*`/`bind`/`listen` (`:995`), while the view/zygote `ChildIo.keep` omits `pinned_socket_fds()` (`:1201-1205`), so an app-controlled view cannot reach the pool at all.

**(3) Is `RLIMIT_NPROC = resolved + 2` still a real bound on a `setsid()` escapee, and is `+2` vs `+16` justified?**
Mechanically yes: it is a per-*real-uid* limit that counts threads, is inherited as both soft and hard, and cannot be raised without `CAP_SYS_RESOURCE` (which `drop_privileges` clears); with `pm=static` the uid already holds `resolved + 1` processes, so an escapee normally has exactly one fork. `+2` is justified against the view's `+16` (`crates/blastit/src/zygote.rs:52,115-121`): php-fpm is master + N children with no interpreter threads, CPython needs interpreter/GC threads. But "bounded" is only meaningful if `resolved` is bounded — today the ceiling is the deployment budget (S-1), so the bound scales with the pool it is supposed to contain. State explicitly that the single spare is also the master's replacement slot: an escapee that forked once makes php-fpm's next replacement `EAGAIN`, decaying the pool to zero workers (a persistent 503). That is a same-route DoS and it is *accepted*; it just should not read as a bounded nuisance.

**(4) Can two FastCGI routes share a directory/inode/pool, or overrun one per-uid `RLIMIT_NPROC`?**
Not with the text as written: indices are distinct, uids are `UID_BASE+1000+i` (distinct, one pool per uid), `B2` requires `(st_dev,st_ino)` distinct from every other route's `parentfd`, and a hardlinked socket is rejected by `st_nlink == 1`. Either route may *count* the full `cap` (their `pm.max_children` sum is `2 × cap`), which is the WSGI arithmetic and is fine for admission (global `slots < max_workers` + per-route permit), but only once `cap` is bounded (S-1). The one way to get a collision is two different definitions of `<route_index>` (S-8), and even then the `peer_uid` check fails closed with `502`/`503` rather than letting route A talk to pool B.

**(5) Does the over-budget refusal fail closed in `dev`, `check`, production `prefork` and lazy, and can init/scheduler disagree into a larger pool?**
Placement is right: `check_fastcgi_workers` runs in `stage0` for production *and* `dev` (`:1137-1146`) and in `check::execute` before any branch (`:104-108`), so both prefork and lazy are covered before any pool exists. The formula cannot disagree: init and the scheduler both take `max_workers`/`view_max_workers` from the same stage-1 document, and `Config::validate` never clamps `view_max_workers` (`crates/blastit/src/config.rs:1301-1321` only rejects `0` and a `checked_add(16)` overflow), so there is no silent shrink to make `pm.max_children < worker_cap` — add a boot `debug_assert_eq!(pinned_workers, state.worker_cap)` anyway as cheap insurance. What *is* missing is that the refusal only covers an **explicit** `workers`; the derived path can exceed 64 without any refusal (S-1). `check`'s parentfd preflight cannot complete as written (S-11).

**(6) Does anything new get printed that leaks a path or a host fact?**
The new `dev` line (`:82`) is stderr-only, carries the route name, the resolved number and the *name* of the budget env var — no path, uid, secret or new JSON key/event. Production prints nothing extra. The derived path is, however, printed in boot diagnostics (`:380`, `:1130`) against §1.2's absolute "never printed" (S-9); pin the rule and keep it out of `--json`/`http_obs.jsonl`.

## 3. Attacked and held (recorded so the architect does not re-litigate)

- `SO_PEERCRED` set is exact and correct given `chown` does not change peer creds: production accepts only `{route_uid:route_gid}` (the binding master), `dev`/`check` only `{invoking_uid:invoking_gid}`, `scheduler_uid` rejected (`:996`, `:1333`). `enforce_socket_inode = true` *is* pinned for production (`:667`), which is what makes a same-uid escapee's socket a `502` rather than a wire MITM.
- `S7` is unforgeable: `ctl.chan` is an unnamed `socketpair` held only by init and scheduler, and `S0`/`S3` exec through `ChildIo { keep: vec![] }`, so no `route_uid` process (including an app-controlled `php-fpm` binary) holds an end (`:1317`, `:1320`, `:1331`).
- No post-boot path resolution of the parent or leaf: the only socket operation is `connect("/proc/self/fd/<parentfd>/<name>")`, the descriptor crosses exactly one `execve` as an argv number, and stage 1 validates `fd >= 3`, uniqueness and `S_ISDIR` before wrapping (`:1183-1205`).
- `B2`'s `RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS` plus per-segment `O_NOFOLLOW` fallback on `ENOSYS` is a genuine magic-link wall; `DevProbe` uses the same predicate and requires `fstat`/`lstat` inode equality on the run root.
- The stage-0 `parentfd` never reaches `http`/`dbproxy`/`view`/`pool`; `BLASTIT_CHECK_POOL_PARENT_FD` is read before `BLASTIT_*` stripping and excluded from `Config::to_json` (`:1219-1226`), so it is not a second handoff source.
- `check_sql_obs_fd` closing before `exec_stage1_dev` means no pool process can forge `WireSqlObs` — unchanged and correct.

## 4. Acceptance condition

Zero MAJORs. S-1, S-2 and S-3 each need a text change **and** a named test before this amendment can be accepted; S-4/S-5 should land with `MB.3.6.3.2` because they are the pool file's own render path, and S-11 must be resolved inside `MB.3.9.3` (it is currently un-implementable as written). The remaining MINORs (S-6…S-10) can be follow-ups but S-9/S-10 are one-sentence doc fixes and should be taken now.
