# Connection pooling for the deploy presets (DO managed pooler, Compose PgBouncer)

- Node: MB.2.11   - Author: researcher   - Date: 2026-11-13

## TL;DR (<= 8 lines)

- A DigitalOcean pool is a **separate resource**, not a switch: direct cluster `:25060`, pool `:25061`, and the pool URI's *database* segment is the **pool name**, not the target database ([API ref](https://docs.digitalocean.com/reference/api/reference/databases/#databases_list_connectionPools)).
- `doctl databases pool create <cluster> <pool> --db <db> --size <n> --mode transaction` enables it; console path is Databases -> cluster -> **Connection Pools** -> Create Pool ([doctl](https://docs.digitalocean.com/reference/doctl/reference/databases/pool/create/), [how-to](https://docs.digitalocean.com/products/databases/postgresql/how-to/manage-connection-pools/)).
- DO's pooler is PgBouncer in **transaction** mode by default; DO names prepared statements, advisory locks and LISTEN/NOTIFY as **session** features, so assume they are unsupported on a pool ([how-to](https://docs.digitalocean.com/products/databases/postgresql/how-to/manage-connection-pools/)).
- PgBouncer transaction mode: `SET`/`RESET`, `LISTEN`, `WITH HOLD` cursors, SQL `PREPARE`/`DEALLOCATE` and session advisory locks are **Never**; protocol-level prepares work only with `max_prepared_statements > 0` ([feature table](https://www.pgbouncer.org/features.html)).
- `max_prepared_statements` exists since **1.21.0**, defaults to **200** since **1.24.0**; psycopg's pooler support wants PgBouncer **>= 1.22** *and* libpq **>= 17** ([changelog](https://www.pgbouncer.org/changelog.html), [psycopg](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html)).
- Django is already pooler-safe: psycopg 3 connections get `prepare_threshold=None` and the default cursor is `ClientCursor`, which never prepares ([base.py](https://github.com/django/django/blob/stable/6.1.x/django/db/backends/postgresql/base.py#L310-L314)).
- `options=-c timezone=UTC` survives PgBouncer (verified on 1.26.1) and makes the server report `UTC`, but a Blastit app cannot use it: `crates/blastit-env`'s `ALLOWED_PARAMETERS` refuses `options` in a `DATABASE_URL` (and `blastit-dbproxy` refuses it in the startup packet). The shipped answer is the role default: `ALTER ROLE app SET timezone = 'UTC'`, which PostgreSQL reports at the startup of each new server session (an open pooled backend keeps its login zone until recycled) ([ALTER ROLE](https://www.postgresql.org/docs/current/sql-alterrole.html), [ParameterStatus](https://www.postgresql.org/docs/current/protocol-flow.html#PROTOCOL-ASYNC)).
- Preset rule: **app -> pooler, migrations -> a literal direct `migrator` URL**; Compose pins `edoburu/pgbouncer:v1.26.1-p0` (MIT image, ISC PgBouncer).

## Developer Experience Implications

- **DO is one command and zero config files**: `doctl databases pool create` yields a URI with `?sslmode=require` on `:25061`; nothing to write, no PgBouncer settings to learn ([API ref](https://docs.digitalocean.com/reference/api/reference/databases/#databases_add_connectionPool)).
- **App Platform needs exactly one bindable**: `${db.<pool>.DATABASE_URL}` (three-part form) for the app. The migrator uses a **literal direct URL** for its own DDL role — `postgresql://migrator:…@<host>:25060/defaultdb?sslmode=require` — never `${db.DATABASE_URL}`, which is the `doadmin` owner ([env vars](https://docs.digitalocean.com/products/app-platform/how-to/use-environment-variables/)).
- **Compose diff is one service and one hostname**: app `DATABASE_URL` host becomes `pgbouncer`, migrator keeps `db`; the pooler needs `DB_HOST`/`DB_USER`/`DB_PASSWORD`/`DB_NAME` plus `POOL_MODE` and `AUTH_TYPE`, and a healthcheck it does not ship ([image README](https://github.com/edoburu/docker-pgbouncer)).
- **Django needs no setting at all** (prepare_threshold already `None`); only raw psycopg/SQLAlchemy users need `prepare_threshold=None`, or `max_prepared_statements>0` on the pooler ([prepare.html](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html)).
- **Timezone is a role setting, not a client statement**: `ALTER ROLE app SET timezone = 'UTC'` (or `ALTER DATABASE`) makes PostgreSQL report `TimeZone = UTC` at the startup of each new server session, an open pooled backend keeping its login zone until recycled ([ALTER ROLE](https://www.postgresql.org/docs/current/sql-alterrole.html), [ParameterStatus](https://www.postgresql.org/docs/current/protocol-flow.html#PROTOCOL-ASYNC)), Django skips `set_config`, and the `[group.connection.db]` grant becomes dead ([Django source](https://github.com/django/django/blob/stable/6.1.x/django/db/backends/postgresql/base.py#L364-L371)). A `DATABASE_URL` cannot carry this: `options` is refused by `crates/blastit-env`.
- **Two failure modes are worth one warning line each**: a pool URI's `dbname` is the pool name (never re-inject the manifest database name), and `edoburu`'s default `AUTH_TYPE=md5` fails against PostgreSQL 18 with `wrong password type` ([entrypoint](https://github.com/edoburu/docker-pgbouncer/blob/master/entrypoint.sh)).
- **Pooling is what makes small per-route pools safe**: Blastit opens one backend connection per worker; the pooler multiplexes many app connections onto `default_pool_size` (20) server connections ([config](https://www.pgbouncer.org/config.html#default_pool_size)).

## Technical Findings

### A. DigitalOcean managed PostgreSQL pooler

- **Enable (console)**: Databases -> cluster -> **Connection Pools** -> **Create Pool** (name, database, user, mode, size) ([how-to](https://docs.digitalocean.com/products/databases/postgresql/how-to/manage-connection-pools/)).
- **Enable (doctl)**: `doctl databases pool create <database-cluster-id> <pool-name> --db <db> --size <n> [--mode transaction|session|statement] [--user <u>]`; `--db` and `--size` required, `--mode` defaults to `transaction` ([doctl pool create](https://docs.digitalocean.com/reference/doctl/reference/databases/pool/create/)). API: `POST /v2/databases/{uuid}/pools` ([API ref](https://docs.digitalocean.com/reference/api/reference/databases/#databases_add_connectionPool)).
- **No cluster-wide switch**: "Once you've created a connection pool, you must use its specific information to force clients to connect to it" ([how-to](https://docs.digitalocean.com/products/databases/postgresql/how-to/manage-connection-pools/)). `doctl databases connection` returns only the direct cluster connection; pool URIs come from `doctl databases pool list` ([doctl](https://docs.digitalocean.com/reference/doctl/reference/databases/pool/list/)).
- **Shape**: pool object is `{"database":"backend-pool","host":"db.example.com","password":"…","port":25061,"ssl":true,"uri":"postgres://doadmin:…@db.example.com:25061/backend-pool?sslmode=require","user":"doadmin"}`; direct is the same host on `25060` ([API ref](https://docs.digitalocean.com/reference/api/reference/databases/#databases_list_connectionPools)). The pool's `db` field (`defaultdb`) is the target database; the URI path is the **pool name**.
- **Mode is fixed at creation**: "Transaction mode is the most common option and is selected for you by default. This setting cannot be modified after creation"; pool name is likewise immutable ([how-to](https://docs.digitalocean.com/products/databases/postgresql/how-to/manage-connection-pools/)). `doctl databases pool update` still exposes `--mode`, so treat that as a docs inconsistency, not a capability ([doctl](https://docs.digitalocean.com/reference/doctl/reference/databases/pool/update/)).
- **Size**: "The pool size is the minimum number of connections the pool can handle. The maximum pool size varies based on the size of the cluster"; backend budget is "25 backend server connections … for every 1GB of RAM. Three are reserved for maintenance" ([API ref](https://docs.digitalocean.com/reference/api/reference/databases/#databases_add_connectionPool)).
- **TLS**: "Managed PostgreSQL clusters require TLS for all connections"; pool URIs ship `ssl: true` + `sslmode=require`, so `require` works on `:25061` ([secure](https://docs.digitalocean.com/products/databases/postgresql/how-to/secure/), [API ref](https://docs.digitalocean.com/reference/api/reference/databases/#databases_list_connectionPools)). Whether the Standard-Edition CA file works for `verify-full` on the pool port is not documented; only `require` is shown.
- **Documented limitations** (verbatim): session mode "is useful when your application uses prepared statements, advisory locks, listen/notify, or other features which operate on a session level rather than a transaction level"; "Using `pg_dump` on a connection pool causes errors when `pool_mode` is set to `transaction`. We recommend you use `pg_dump` directly against your database cluster, bypassing its connection pool(s)." ([how-to](https://docs.digitalocean.com/products/databases/postgresql/how-to/manage-connection-pools/)).
- **Prepared statements**: DO never states a PgBouncer version or `max_prepared_statements` value and never claims protocol-level prepares work in transaction mode; the only documented answer is "use session mode" (above). Treat transaction pools as prepared-statement-unsafe until tested per cluster.
- **Startup `options`**: no DO page documents it. The cluster config schema exposes `pgbouncer.ignore_startup_parameters` with an enum of only `extra_float_digits`/`search_path`, and a cluster-level `timezone` parameter ([API ref](https://docs.digitalocean.com/reference/api/reference/databases/#databases_patch_config)). Unverified for the pool port; the documented alternative is `doctl databases configuration update <db-id> --engine postgres --config-json '{"timezone":"UTC"}'` ([doctl](https://docs.digitalocean.com/reference/doctl/reference/databases/configuration/update/)).

### B. PgBouncer

- **Transaction semantics**: "A server connection is assigned to a client only during a transaction… This mode breaks a few session-based features of PostgreSQL" ([features](https://www.pgbouncer.org/features.html)). Per-feature: `SET`/`RESET` **Never**, `LISTEN` **Never**, `NOTIFY` Yes, `WITHOUT HOLD` Yes, `WITH HOLD` **Never**, protocol-level prepared plans **Yes** (only with `max_prepared_statements` non-zero), SQL `PREPARE`/`DEALLOCATE` **Never**, `ON COMMIT DROP` temp tables Yes, `PRESERVE/DELETE ROWS` **Never**, `LOAD` **Never**, session advisory locks **Never** ([feature table](https://www.pgbouncer.org/features.html)). "Never" means silently wrong, not rejected: the statement runs on whichever server connection is attached ([config](https://www.pgbouncer.org/config.html#server_reset_query)). A backend keeps the session GUCs it logged in with until it is recycled; `server_lifetime` defaults to **3600 s** and `server_reset_query` only runs on reset ([config](https://www.pgbouncer.org/config.html#server_lifetime)).
- **`max_prepared_statements`**: added in **1.21.0** ("The one with prepared statements"), "you need to change the new `max_prepared_statements` setting to a non-zero value"; **Default: 200** since 1.24.0 ("Enable prepared statement support by default") ([changelog](https://www.pgbouncer.org/changelog.html), [config](https://www.pgbouncer.org/config.html#max_prepared_statements)). It rewrites client names to `PGBOUNCER_{unique_id}` and prepares on whichever server the client lands on; it does **not** touch SQL-level `PREPARE`/`EXECUTE`/`DEALLOCATE`.
- **Error when it is 0**: PgBouncer forwards `Parse`/`Bind` unchanged and PostgreSQL raises `prepared statement "_pg3_0" already exists` (42P05) or `prepared statement "_pg3_0" does not exist` (26000) ([prepare.c](https://github.com/postgres/postgres/blob/master/src/backend/commands/prepare.c)). Probe (`edoburu/pgbouncer:v1.26.1-p0`, `pool_mode=transaction`, `max_prepared_statements=0`, 6 psycopg 3 clients): `psycopg.errors.DuplicatePreparedStatement: prepared statement "_pg3_0" already exists` and `psycopg.errors.InvalidSqlStatementName: prepared statement "_pg3_0" does not exist`; with `MAX_PREPARED_STATEMENTS=200` the same 240-query run had 0 errors.
- **Sizing defaults** ([config](https://www.pgbouncer.org/config.html)): `pool_mode` default `session`; `default_pool_size` **20** (server connections per user/database pair); `max_client_conn` **100**; `reserve_pool_size` **0**; `reserve_pool_timeout` **5.0**; `min_pool_size` **0**.
- **Auth**: `auth_type` = `cert`, `md5` (default), `scram-sha-256`, `plain` (deprecated), `trust`, `any`, `hba`, `ldap`, `pam`; "Most authentication types … require that either `auth_file` or `auth_user` be set". `userlist.txt` lines are `"user" "password"`, `"user" "md5…"`, or `"user" "SCRAM-SHA-256$<iterations>:<salt>$<storedkey>:<serverkey>"` ([config](https://www.pgbouncer.org/config.html#auth_type), [file format](https://www.pgbouncer.org/config.html#authentication-file-format)). A SCRAM secret avoids plaintext, but it only logs in to the backend when PgBouncer auth is also SCRAM, the database entry forces no user, and the secrets are identical (same salt/iterations); otherwise use `auth_user` + a SECURITY DEFINER `auth_query` returning `(rolname, rolpassword)` ([config](https://www.pgbouncer.org/config.html#auth_query)).
- **Healthcheck**: the image ships **no** `HEALTHCHECK` (verified: `docker inspect … .Config.Healthcheck == null`), but bundles `pg_isready` and listens on **5432**, not 6432 ([Dockerfile](https://github.com/edoburu/docker-pgbouncer/blob/master/Dockerfile)). Portable probe: `pg_isready -h 127.0.0.1 -p 5432 -U <user>` — it "is not necessary to supply correct user name, password, or database name" ([pg_isready](https://www.postgresql.org/docs/current/app-pg-isready.html)); verified exit 0 through a transaction-mode pooler. `SHOW POOLS` is the backend-aware probe but needs the `pgbouncer` admin database, `admin_users`, and simple-query protocol only ([usage](https://www.pgbouncer.org/usage.html)) — do not use it as a container healthcheck.
- **Image**: current tag `edoburu/pgbouncer:v1.26.1-p0` (2026-10-19, ~19 MB), which fixes CVE-2026-107350/107349/107348 ([tags](https://hub.docker.com/v2/repositories/edoburu/pgbouncer/tags?page_size=40), [changelog](https://www.pgbouncer.org/changelog.html)). PgBouncer is **ISC** ([COPYRIGHT](https://github.com/pgbouncer/pgbouncer/blob/master/COPYRIGHT)); the image repo is **MIT** ([LICENSE](https://github.com/edoburu/docker-pgbouncer/blob/master/LICENSE)) — both Apache-2.0-compatible. Env config covers `DB_HOST/DB_PORT/DB_USER/DB_PASSWORD/DB_NAME`, `LISTEN_PORT`, `AUTH_TYPE`, `AUTH_USER`, `AUTH_QUERY`, `POOL_MODE`, `DEFAULT_POOL_SIZE`, `MAX_CLIENT_CONN`, `MAX_PREPARED_STATEMENTS`, `IGNORE_STARTUP_PARAMETERS`, `CLIENT_TLS_*`/`SERVER_TLS_*`; `track_extra_parameters` and per-database `pool_size` need a mounted `pgbouncer.ini` ([entrypoint](https://github.com/edoburu/docker-pgbouncer/blob/master/entrypoint.sh)).
- **`options` startup parameter**: supported since **1.20.0** ([changelog](https://www.pgbouncer.org/changelog.html)); unknown top-level params are rejected, but parameters inside `options` are supported when tracked: "it's not possible to include `options` itself in `track_extra_parameters`, only the parameters contained in `options`" ([config](https://www.pgbouncer.org/config.html#track_extra_parameters)). `TimeZone` is tracked by default, so `options=-c timezone=UTC` works with zero configuration (probe: `UTC` through the pooler vs `Etc/UTC` without); an untracked one is rejected: `FATAL: unsupported startup parameter in options: statement_timeout` (probe). `ignore_startup_parameters` defaults to empty and only *drops* what it lists ([config](https://www.pgbouncer.org/config.html#ignore_startup_parameters)). A Blastit app cannot use this: `crates/blastit-env`'s `ALLOWED_PARAMETERS` refuses `options` in the input URL, and `blastit-dbproxy` refuses it in the client startup packet.

### C. Client side: psycopg 3 / Django

- **psycopg 3 prepares after `prepare_threshold`**: default **5**, computed per connection, `_pg3_N` names, `prepared_max=100`; disable with `prepare_threshold=None` (connect kwarg since 3.1 or attribute) ([prepare.html](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html), [connections](https://www.psycopg.org/psycopg3/docs/api/connections.html#psycopg.Connection.prepare_threshold)). psycopg's own warning: poolers are "not compatible with prepared statements, because the same client connection may change the server session it refers to" ([prepare.html](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html)).
- **`options` is a libpq startup parameter**: "command-line options to send to the server at connection start", `-c name=value` sets the session value ([libpq](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-PARAMKEYWORDS)); psycopg passes any libpq keyword through ([connections](https://www.psycopg.org/psycopg3/docs/api/connections.html#psycopg.Connection.connect)).
- **Django `_configure_timezone`** ([base.py](https://github.com/django/django/blob/stable/6.1.x/django/db/backends/postgresql/base.py#L364-L371)): reads `connection.info.parameter_status("TimeZone")`, compares with `self.timezone_name`, and only on mismatch runs `SELECT set_config('TimeZone', %s, false)` ([operations.py](https://github.com/django/django/blob/stable/6.1.x/django/db/backends/postgresql/operations.py#L197-L198)). `is_local=false` makes it session-wide, so it is not rolled back by Django's commit ([functions-admin](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADMIN-SET)).
- **What it compares against is not `settings.TIME_ZONE` directly**: with `USE_TZ=True` (default) and no per-database `TIME_ZONE`, Django wants `"UTC"`; `settings.TIME_ZONE` only drives the connection when `USE_TZ=False` or `DATABASES[...]["TIME_ZONE"]` is set ([base.py](https://github.com/django/django/blob/stable/6.1.x/django/db/backends/base/base.py#L157-L167), [docs](https://docs.djangoproject.com/en/6.1/ref/settings/#time-zone)).
- **`OPTIONS` reaches libpq**: connection params are `{"dbname": …, **settings_dict["OPTIONS"]}` then handed to `psycopg.connect()` ([base.py](https://github.com/django/django/blob/stable/6.1.x/django/db/backends/postgresql/base.py#L270-L279)), so `OPTIONS: {"options": "-c timezone=UTC"}` is the supported way to set a startup GUC.
- **The `set_config` query is never prepared**: Django sets `prepare_threshold=None` for psycopg 3 ("Disable prepared statements by default to keep connection poolers working"), and its cursor subclasses `ClientCursor`, whose `_get_prepared()` always returns `Prepare.NO` ([base.py](https://github.com/django/django/blob/stable/6.1.x/django/db/backends/postgresql/base.py#L310-L314), [client_cursor.py](https://github.com/psycopg/psycopg/blob/master/psycopg/psycopg/client_cursor.py)). Even with server-side binding it runs once per connection (1 < 5).
- **With `max_prepared_statements >= 1`**: psycopg's default "works" only on PgBouncer **>= 1.22** with `max_prepared_statements > 0` and client libpq **>= 17**; otherwise set `prepared_max=None` or `prepare_threshold=None` ([prepare.html](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html), [1.22 changelog](https://www.pgbouncer.org/changelog.html)). 1.21 alone is not enough for psycopg 3.
- **`sslmode`/`channel_binding`**: client TLS terminates at the pooler (`client_tls_sslmode` default `disable`; backend TLS is separate, `server_tls_sslmode` default `prefer`), so `verify-full` validates the **pooler's** certificate, not the origin ([config](https://www.pgbouncer.org/config.html#client_tls_sslmode)). PgBouncer does not implement SCRAM channel binding, so `channel_binding=require` fails; use `prefer` (libpq default) ([issue #522](https://github.com/pgbouncer/pgbouncer/issues/522), [libpq](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-CHANNEL-BINDING)).
- **Runtime detection**: PgBouncer 1.26 sends `pgbouncer.version`, `pgbouncer.pool_mode` and `pgbouncer.max_prepared_statements` as ParameterStatus on login "so clients and drivers can detect that they are connected through PgBouncer and adapt" ([changelog](https://www.pgbouncer.org/changelog.html)); verified through psycopg 3 on 1.26.1: `conn.info.parameter_status("pgbouncer.pool_mode")` -> `transaction`, `("pgbouncer.max_prepared_statements")` -> `200`, `("pgbouncer.version")` -> `1.26.1`.

### The one question: does Django still run `set_config` behind the pooler?

- **VERIFIED**: `ALTER ROLE app SET timezone = 'UTC'` makes PostgreSQL report `TimeZone = UTC` in the startup ParameterStatus ([ALTER ROLE](https://www.postgresql.org/docs/current/sql-alterrole.html), [protocol-flow](https://www.postgresql.org/docs/current/protocol-flow.html#PROTOCOL-ASYNC)); `SHOW TimeZone` and psycopg `info.parameter_status("TimeZone")` both return exactly `UTC` (probes on PostgreSQL 18.7; a server default set as `Etc/UTC` stays `Etc/UTC`).
- **VERIFIED from source**: Django compares that string with `timezone_name` (`"UTC"` under `USE_TZ=True`). Equal -> branch skipped; a per-database `TIME_ZONE="America/New_York"` -> one `set_config` per connection ([base.py](https://github.com/django/django/blob/stable/6.1.x/django/db/backends/postgresql/base.py#L364-L371)).
- **Therefore**: with the role default, the `set_config` round trip disappears and `[group.connection.db]` is a dead grant wherever the session says `UTC` — confirmed by `python/tests/test_check.py::_django_manifest()` (no group iff `parameter_status("TimeZone") == "UTC"`) and `crates/blastit/src/audit_v1.rs::dead_group_grants` (an unused group query is `DeadGrant{severity: Error}`). `options=-c timezone=UTC` would do the same, but it is **not available to a Blastit app**: `crates/blastit-env`'s `ALLOWED_PARAMETERS` refuses `options`, deliberately, so a URL cannot set runtime parameters.

## Concrete Recommendations for Blastit

1. **Two destinations, visible in every snippet**: app `DATABASE_URL` -> pooler; `migrate` -> a literal direct URL for its own DDL role. DO: `${db.<pool>.DATABASE_URL}` vs `postgresql://migrator:…@<host>:25060/defaultdb?sslmode=require` — never `${db.DATABASE_URL}`, which is the `doadmin` owner ([App Platform](https://docs.digitalocean.com/products/app-platform/how-to/use-environment-variables/)). Compose: `postgres://…@pgbouncer:5432/shop` vs `postgres://…@db:5432/shop`.
2. **Never re-inject `dbname`**: take it from the URI; for DO it is the pool name, while the real database is the pool's `db` field ([API ref](https://docs.digitalocean.com/reference/api/reference/databases/#databases_list_connectionPools)).
3. **Make the role's zone UTC** instead of documenting a `set_config` grant: `ALTER ROLE app SET timezone = 'UTC'` (DO role SQL, Compose `db/grants.sql`). PostgreSQL reports it at the startup of each new server session (an open pooled backend keeps its login zone until recycled; `server_lifetime` is 3600 s) ([ALTER ROLE](https://www.postgresql.org/docs/current/sql-alterrole.html)), Django's `_configure_timezone` is a no-op, and `[group.connection.db]` is dead where the session says `UTC` — it stays only for a database that says another spelling (CI's `postgres:18`). A `DATABASE_URL` cannot carry `options`: `crates/blastit-env` refuses it, and that allowlist is deliberate.
4. **Compose pooler service**: `image: edoburu/pgbouncer:v1.26.1-p0`, `POOL_MODE=transaction`, `AUTH_TYPE=scram-sha-256` (md5 fails against PG 18), explicit `MAX_PREPARED_STATEMENTS=200` (survives a downgrade to 1.21–1.23 where the default is 0), `DEFAULT_POOL_SIZE=20`, secrets from the environment, `healthcheck: pg_isready -h 127.0.0.1 -p 5432 -U $DB_USER`, `depends_on: db: {condition: service_healthy}`.
5. **Do not mount a `pgbouncer.ini`** unless a knob is missing from env; the entrypoint generates it and sets `ignore_startup_parameters = extra_float_digits` by default ([entrypoint](https://github.com/edoburu/docker-pgbouncer/blob/master/entrypoint.sh)).
6. **Prepared statements**: document Django as safe (default `prepare_threshold=None`); for raw psycopg/SQLAlchemy show `prepare_threshold=None` (one line, works on any pooler) rather than requiring `max_prepared_statements`.
7. **Pooler-agnostic runtime check**: if Blastit's dbproxy can read ParameterStatus, warn when `pgbouncer.pool_mode=transaction` and `pgbouncer.max_prepared_statements=0` while the client prepares (PgBouncer >= 1.26) ([changelog](https://www.pgbouncer.org/changelog.html)).
8. **Do not put `channel_binding=require` in preset URLs**; `sslmode=require` (DO) / `verify-full` against the pooler cert is the honest ceiling ([issue #522](https://github.com/pgbouncer/pgbouncer/issues/522)).
9. **Keep the privilege contract**: adding a pooler changes connection arithmetic, not isolation; presets still fail closed without root/capabilities + seccomp ([deploy index](../deploy/index.md)).

## Unverified / Open Questions

- DO's PgBouncer **version** and `max_prepared_statements` value are not documented anywhere; protocol-level prepared statements in transaction mode must be tested per cluster. Two probes settle it: `psycopg.connect(pool_dsn).info.parameter_status("pgbouncer.version")` / `("pgbouncer.max_prepared_statements")` (both `None` on PgBouncer < 1.26), then one parameterised query executed more than five times across several concurrent connections.
- Whether DO's `timezone=UTC` cluster config applies without a restart, and whether the pool's hostname always equals the cluster hostname (docs only show examples).
- Whether `verify-full` with the Standard-Edition CA works on `:25061` (only `require` is documented).
- Whether Blastit's dbproxy forwards extended-protocol `Parse`/`Bind` names unchanged (decides if `max_prepared_statements` is load-bearing for us) — needs a read of `crates/blastit-dbproxy`.
- `edoburu/pgbouncer` is a community image, not a Docker Official image; no upstream support statement found.
